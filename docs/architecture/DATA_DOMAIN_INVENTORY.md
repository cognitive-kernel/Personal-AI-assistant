# موجودی حوزه‌های داده و مسیرهای دسترسی

- تاریخ ممیزی: 2026-10-15
- شاخه مبنا: `main`
- دامنه: ممیزی استاتیک فایل‌های موجود از GitHub؛ checkout کامل و اجرای تست در این مرحله انجام نشده است.
- هدف: تعیین مرزهای داده بر اساس مالکیت و رفتار واقعی، نه انتخاب تعداد ثابت پایگاه داده.

## یافته‌های تأییدشده از کد

| حوزه | محل/مسیر فعلی | وضعیت مشاهده‌شده | نتیجه برای طراحی |
|---|---|---|---|
| تنظیمات | `app/config.py`, `app/db.py`; `settings_connection()` | فایل SQLite مستقل با مسیر تنظیم‌پذیر؛ مقادیر JSON در جدول `settings` | مرز فعلی مستقل بماند؛ قرارداد مخزن تنظیمات و نسخه‌بندی schema لازم است |
| یادگیری و دانش | `app/learning.py`, `app/db.py`; `learning_connection()` | `learning_jobs`, `learning_source_text`, `learning_evidence`, `knowledge_items`, ارزیابی‌ها و مسیر یادگیری در یک فایل learning | فعلاً داده‌های به‌هم‌پیوسته‌اند؛ جداسازی آن‌ها بدون نقشه وابستگی و مهاجرت آزموده‌شده خطرناک است |
| صف وظایف | `app/task_manager.py` | جدول `task_queue` با checkpoint، lease و وضعیت؛ در همان پایگاه learning ایجاد می‌شود | صف فعلاً از نظر ماژولی مستقل ولی از نظر فایل فیزیکی مستقل نیست؛ مرز مستقل باید پس از بررسی تراکنش‌ها و عملیات بازیابی تعیین شود |
| اجرای وظایف | `app/task_worker.py`, `app/task_runtime.py` | dispatcher فقط handler ثبت‌شده را اجرا می‌کند؛ runtime در startup/shutdown برنامه به handler واقعی یادگیری متصل است | وظایف یادگیری از صف پایدار اجرا می‌شوند؛ registry همچنان فقط handlerهای ثبت‌شده را می‌پذیرد |
| اجرای یادگیری | `app/learning.py` | ارسال API و مسیرهای یادگیری به task `learning.generate` انجام می‌شود؛ executor حافظه‌ای قدیمی حذف شده است | dedupe بر اساس شناسه job، retry محدود، lease/heartbeat و reconcile در startup برای jobهای orphaned فراهم شده‌اند؛ هماهنگی کامل توقف/بازیابی همچنان نیازمند آزمون‌های یکپارچگی است |
| گزارش عملیاتی و ممیزی | logging و ستون‌های خطا/زمان در ماژول‌ها | از ممیزی استاتیک، مخزن مستقل رویداد/audit با قرارداد و سیاست نگهداری اثبات نشد | نیاز به بررسی کامل مسیرهای log و نیازهای نگهداری؛ فعلاً تصمیم به دیتابیس مستقل قطعی نیست |
| آرشیو مکالمه | مسیرهای API گفتگو و history ورودی | ذخیره‌سازی canonical مکالمه از شواهد بررسی‌شده تأیید نشد؛ تاریخچه API به‌صورت ورودی محدودشده دریافت می‌شود | پیش از ایجاد مخزن، باید رفتار فعلی و الزامات حریم خصوصی/حذف مشخص شوند |
| ایندکس بازیابی | جست‌وجوی lexical/vector | مخزن canonical یا ایندکس مستقل در فایل‌های بررسی‌شده مشاهده نشد | هنوز داده واقعی برای انتخاب موتور یا ایجاد دیتابیس ایندکس وجود ندارد |
| گراف دانش | مسیرهای یادگیری و پیش‌نیازها | داده‌های مسیر و موضوع‌ها رابطه‌های ساختاری دارند؛ گراف عمومی و مستقل اثبات نشد | ابتدا نیازهای traversal و query اندازه‌گیری شود؛ جدول رابطه‌ای مستقل تنها در صورت توجیه ساخته شود |

## ریسک‌های باقی‌مانده پس از اتصال صف و یادگیری

1. task و learning job در یک فایل SQLite نگهداری می‌شوند، اما ایجاد job و task هنوز یک تراکنش واحد نیست؛ reconcile در startup رکوردهای orphaned را بازیابی می‌کند.
2. توقف تعاونی هنگام فراخوانی طولانی مدل فوری نیست؛ نتیجه پس از بازگشت فراخوانی مدل کنار گذاشته می‌شود و task در checkpoint بعدی وضعیت pause/cancel را ثبت می‌کند.
3. lease و heartbeat از بازیابی task حمایت می‌کنند، اما crash در مرزهای بین commit وضعیت یادگیری و commit وضعیت task باید با آزمون‌های fault-injection و restart پوشش داده شود.
4. `app/db.py` هنوز migration runner نسخه‌دار عمومی و سیاست کامل rollback/restore ندارد.

## تصمیم فعلی دربارهٔ مرزهای ذخیره‌سازی

- فقط دو فایل SQLite با مسیر مستقل از تنظیمات پیکربندی و یک فایل learning حاوی چند حوزهٔ مرتبط در این ممیزی تأیید شده‌اند؛ این به‌معنای آن نیست که دو فایل فعلی مرزهای نهایی هستند.
- فعلاً دیتابیس جدیدی برای تجربه، مکالمه، retrieval یا graph ساخته نمی‌شود، چون مالکیت و جریان داده‌های واقعی هنوز کامل نشده‌اند.
- ابتدا قراردادهای مخزن و migration/versioning برای ذخیره‌سازی موجود تعریف می‌شوند؛ سپس حوزه‌های تجربه، audit، conversation، retrieval و graph با ماتریس مالکیت، حجم، حریم خصوصی، دسترسی و بازیابی ارزیابی خواهند شد.
- جداسازی فیزیکی صف از learning فقط پس از تعیین تراکنش‌ها، idempotency، outbox/reconciliation و آزمون recovery تصمیم‌گیری می‌شود.
- هیچ داده‌ای در این ممیزی منتقل یا حذف نشده است.

## گام اجرایی بعدی

گام بعدی: اجرای CI روی head دقیق PR و سپس افزودن آزمون‌های integration برای startup/shutdown واقعی FastAPI، توقف/ادامه از task API، crash/restart در نقاط مرزی و هماهنگی وضعیت job و task. پس از عبور این آزمون‌ها، به ممیزی کامل schemaها و migration runner نسخه‌دار برویم.
