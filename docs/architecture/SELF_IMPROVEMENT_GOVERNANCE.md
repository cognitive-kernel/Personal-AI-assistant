# حاکمیت چرخهٔ خودبهبود کد

## هدف و وضعیت

این مرحله چرخهٔ کنترل‌شدهٔ پیشنهاد تغییر کد، بررسی قالب، آزمون رفتاری ایزوله و ایجاد PR پیش‌نویس را فراهم می‌کند. patch روی checkout اصلی اعمال نمی‌شود و merge یا استقرار خودکار انجام نمی‌شود.

## چرخهٔ وضعیت

1. proposed: diff، دلیل تغییر، hash و commit پایه ذخیره می‌شوند.
2. validated: قالب diff و فهرست مسیرها بررسی می‌شوند و git apply --check بدون نوشتن فایل روی همان commit پایه موفق می‌شود.
3. static_checked: پس از رضایت فعال Sandbox و تأیید صریح، patch فقط در Git worktree موقت اعمال می‌شود؛ parser ثابت داخل کانتینر digest-pinned فایل‌های Python را با AST بررسی می‌کند و سپس آزمون‌های رفتاری پروژه در کانتینر آزمون جداگانه، با شبکهٔ غیرفعال و فایل‌های نامزد فقط‌خواندنی اجرا می‌شوند. کد نامزد در محیط ایزولهٔ آزمون اجرا می‌شود، نه در فرایند اصلی برنامه یا checkout اصلی.
4. approved_for_pr: کاربر پس از عبور از بررسی نحوی و آزمون رفتاری ایزوله و با تأیید صریح اجازه می‌دهد پیشنهاد برای بررسی انسانی/PR ادامه پیدا کند. این وضعیت به معنی merge یا استقرار نیست.
5. rejected: پیشنهاد رد می‌شود. رخدادها در جدول تاریخچه باقی می‌مانند.

## محدودیت‌های امنیتی

- API فقط از loopback پذیرفته می‌شود.
- فعال‌سازی به تنظیم صریح SELF_IMPROVEMENT_REPO_ROOT با مسیر مطلق یک checkout Git شامل app/ و tests/ نیاز دارد.
- فقط فایل‌های Python زیر app/ و tests/ و فایل‌های Markdown زیر docs/ مجازند؛ حداکثر ۲۰ فایل و ۲۵۶ KiB در هر diff.
- مسیرهای traversal، rename، delete، symlink، submodule، binary diff و تغییر mode فایل رد می‌شوند. مسیرهای دارای symlink نیز رد می‌شوند.
- مرحلهٔ Git فقط سازگاری diff با HEAD را بررسی می‌کند. گزارش بررسی نحوی به‌تنهایی اجرای آزمون را ادعا نمی‌کند؛ گزارش مرحلهٔ static-check جداگانه نتیجهٔ آزمون رفتاری، وضعیت اجرای ایزوله، hashها و محافظت یکپارچگی تست‌ها را ثبت می‌کند. اگر Docker، image ثابت، رضایت یا آزمون رفتاری معتبر در دسترس نباشد، تأیید متوقف می‌شود.
- HEAD باید بین ثبت، اعتبارسنجی و تأیید ثابت بماند؛ تغییر آن اعتبارسنجی/تأیید را متوقف می‌کند.
- endpoint بررسی نامزد به رضایت Sandbox نیاز دارد؛ image باید از قبل موجود و digest-pinned باشد و اجرای آزمون بدون شبکه انجام می‌شود. patch در worktree موقت اعمال می‌شود و checkout اصلی تغییر نمی‌کند. انتشار PR فقط با تأیید صریح انجام می‌شود؛ merge، deploy و تغییر پایگاه دادهٔ عملیاتی خودکار نیستند.

## وضعیت تکمیل و محدودیت‌های باقی‌مانده

- اجرای آزمون‌های رفتاری در worktree موقت و کانتینر digest-pinned با شبکهٔ غیرفعال پیاده‌سازی شده است؛ تست‌های واحد، شکست آزمون و جلوگیری از تضعیف تست‌ها در CI پوشش دارند.
- گزارش مرحلهٔ بررسی، نتیجهٔ آزمون، وضعیت اجرا و hash پیشنهاد را ثبت می‌کند؛ انتشار PR نیازمند تأیید صریح است و ساخت PR تکراری idempotent است.
- ساخت PR بازگشت برای PR اصلیِ ادغام‌شده پیاده‌سازی شده است؛ اگر فایل تغییرکرده پس از merge تغییر کرده باشد، عملیات fail-closed می‌شود و فقط PR پیش‌نویس برای بررسی انسانی ساخته می‌شود.
- CI و تست‌های شبیه‌سازی‌شده جایگزین اجرای مستقل و عملیاتی روی میزبان هدف یا بازبینی امنیتی نیستند. Issue #52 همچنان نیازمند ارزیابی مستقل است.
- merge، deploy، اعمال خودکار patch روی برنامهٔ در حال اجرا و provisioning/remote execution عمداً غیرفعال‌اند.

این قابلیت «چرخهٔ پیشنهاد، آزمون ایزوله و PR تحت کنترل انسان» است، نه خودبهبود خودکار.
