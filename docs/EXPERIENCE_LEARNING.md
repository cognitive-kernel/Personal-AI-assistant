# Evidence-backed experience learning

The current increment provides persistent experience records and reuses only records marked `verified` in the learning-job prompt. Cross-language retrieval expands the original topic through the configured local Ollama model, searches the existing source index with both the original query and variants, and matches prior verified experiences against the same variants. If the local source index is thin, the job now attempts real web discovery through DuckDuckGo HTML, filters results to an explicit allowlist of official technical-documentation hosts, fetches pages through the existing HTTPS/redirect/DNS/size policy, and indexes accepted pages. If query expansion or discovery fails, the learning job falls back without treating the failed attempt as evidence.

## Experience API

- `POST /api/learning/experiences` — record a weakness or failure.
- `GET /api/learning/experiences` — list/filter experiences by topic or status.
- `GET /api/learning/experiences/{id}` — inspect the complete record.
- `PATCH /api/learning/experiences/{id}` — attach source evidence, test plan/results, and update status/takeaway.

## Evidence and status

An experience cannot be marked `verified` unless it has at least one HTTPS source-evidence item, a test plan, and at least one passing test result. This is a structural guard only: the API does not independently verify that the URL supports the claim or that a caller actually executed the declared test. Treat these records as trusted reusable guidance only when the evidence and test results were produced by the application’s controlled workflow.

Source excerpts and URLs are kept in their original language. The generated lesson language is selected from the topic/request; English source text is not translated before being stored or retrieved. A lesson rejected by the final heuristic quality gate is automatically recorded as a `needs_review` experience with the quality-gate result. This captures a failure signal but does not independently identify a factual error.

## Remaining work before calling this a complete autonomous loop

- More robust provider integration/observability for web search (current HTML scraping is intentionally best-effort and may be blocked or change markup).
- Source relevance/trust evaluation tied to claims, not just HTTPS URL shape.
- Controlled test execution and recorded stdout/exit code/environment, rather than accepting caller-supplied pass/fail alone.
- Bounded retry after a failed test, regression checks, and promotion to `verified` only from results generated by that execution path.
- A fully automated failure-detection -> research -> controlled test -> bounded retry/learning -> persistence -> later reuse loop with end-to-end tests.

Do not describe the complete loop as finished until those behaviors are implemented and tested.
