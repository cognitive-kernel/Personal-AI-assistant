# Evidence-backed experience learning

The adaptive loop is now used by the normal chat endpoint for technical, troubleshooting, and explicit research requests; ordinary small talk keeps the direct chat path. It drafts an initial answer, expands the query across languages, searches/indexes approved official documentation when the local index is thin, reuses verified experiences and failure warnings, asks the local model to revise with source context, retries once for missing URL citations or deterministic Python/JSON syntax errors, and records deterministic verification results. Python and JSON code blocks are parsed but never executed. The learning-job path also uses the same persistent experience memory and its own bounded repair checks. Cross-language retrieval expands the original topic through the configured local Ollama model, searches the existing source index with both the original query and variants, and matches prior verified experiences against the same variants. If the local source index is thin, lacks source diversity, or returns weak lexical matches, the job attempts real web discovery through DuckDuckGo HTML, filters results to an explicit allowlist of official technical-documentation hosts, fetches pages through the existing HTTPS/redirect/DNS/size policy, and indexes accepted pages. If query expansion or discovery fails, the learning job falls back without treating the failed attempt as evidence.

## Single-user feedback memory

The local chat UI can record a `helpful` or `unhelpful` rating and an optional correction through `POST /api/chat/feedback`. Relevant records are retrieved by bounded lexical overlap and supplied to subsequent Ollama prompts as style/quality guidance. The technical revision prompt receives the same guidance. Feedback is not factual evidence, does not override the current user request, and does not automatically mark an experience verified. Review stored feedback with `GET /api/chat/feedback`; it remains local in the learning database.

## Experience API

- `POST /api/learning/experiences` — record a weakness or failure.
- `GET /api/learning/experiences` — list/filter experiences by topic or status.
- `GET /api/learning/experiences/{id}` — inspect the complete record.
- `GET /api/learning/experiences/{id}/versions` — inspect the current version and immutable prior snapshots. Rollback remains an internal controlled-runner operation.
- `PATCH /api/learning/experiences/{id}` — attach source evidence, test plan/results, and update status/takeaway.

## Controlled verification loop

Every accepted learning artifact now runs a bounded deterministic verifier. It checks that at least one retrieved source is relevant to the requested topic, checks the language-aware quality gate and target length, requires exactly three non-empty learning outcomes/questions/answer keys (extra items are rejected rather than silently truncated), checks exact source URL attribution, validates saved source excerpts against retrieved text using SHA-256, and parses fenced Python/JSON examples without executing them. Failed quality, contract, citation, or syntax checks trigger one bounded model repair; remaining failures are recorded and rejected or kept as `needs_review`. The run, test names, outcomes, source language, and verification scope are persisted with the experience. A record without a real retrieved source excerpt cannot become `verified`. The public API cannot promote records to `verified` directly.

The verifier does not execute model-generated code or shell commands. For technical chat answers, a second skeptical pass asks the configured local Ollama model to classify material claims as `supported`, `contradicted`, or `insufficient_evidence` against the retrieved excerpts. The review is schema-validated, every cited evidence URL must come from the retrieved set, and malformed or incomplete output fails closed to `needs_review`. Answer citations are matched as exact HTTPS URL tokens, not substrings: a longer path or query string containing an allowed source URL does not count as citing that source. Sentence punctuation and unmatched Markdown closing delimiters are stripped during token extraction. A citation URL alone never establishes claim support. An experience can become reusable only when deterministic checks and this claim review pass. This is model-assisted review using the same local model, not independent proof; it can still make mistakes. The `verified` status does not mean arbitrary code was runtime-tested or factual truth was externally established. Related `failed`/`needs_review` records are retrieved separately and supplied as cautionary context, never as verified guidance. Unsupported test types remain `needs_review`; the system does not invent a passing test.

## Evidence and status

Only the internal learning workflow can promote an experience to `verified`; the public PATCH endpoint cannot set that status or mutate an already verified record. The workflow records actual deterministic check outcomes, exact source excerpts, excerpt SHA-256 hashes, source language, runner version, and research-attempt metadata. For technical chat, the stored `semantic_claim_review` result includes claim-level verdicts and exact evidence URLs. This is a skeptical second pass from the same local Ollama model, so it improves traceability but is not an independent fact-checker and must not be treated as infallible. Consumers must not interpret `verified` as proof of scientific correctness or runtime behavior outside the recorded test scope.

Source excerpts and URLs are kept in their original language. The generated lesson language is selected from the topic/request; English source text is not translated before being stored or retrieved. A lesson rejected by the final heuristic quality gate is automatically recorded as a `needs_review` experience with the quality-gate result. This captures a failure signal but does not independently identify a factual error.

## Operational boundaries

- Web discovery uses best-effort DuckDuckGo HTML parsing, then permits page ingestion only from the explicit official-documentation host allowlist and through the existing HTTPS, redirect, DNS, content-type, and size controls. Provider markup/network changes can make discovery return no sources; that failure is recorded and does not become evidence.
- Supported checks include deterministic quality/assessment contracts, topic-level source relevance, source attribution and excerpt SHA-256 integrity, Python/JSON syntax parsing, and a task-specific read-only SQLite sandbox over fresh synthetic `users`/`orders` tables (`POST /api/learning/sql-sandbox`). The SQL sandbox has a query timeout, result-row limit, function allowlist, and denies writes, PRAGMA, ATTACH, and extension loading. It does not execute arbitrary Python/shell, access the user's database, or establish semantic truth. Retrieval relevance remains lexical/embedding-based; claim-level semantic review is model-assisted and can fail or be wrong, so human review and external evaluation remain necessary. Tasks requiring real data, hardware, or external services remain `needs_review` unless a dedicated safe verifier exists.
- A separate local end-to-end run with the user's configured Ollama model and live network is environment-specific and must be performed after pulling. CI mocks Ollama/network edges and validates the orchestration and deterministic checks; it cannot guarantee the local model's behavior or live search availability.
