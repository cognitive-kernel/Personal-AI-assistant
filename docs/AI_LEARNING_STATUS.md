# وضعیت اجرایی یادگیری هوش مصنوعی از ChatGPT

آخرین بازبینی: 2026-10-31

این سند وضعیت واقعی پیاده‌سازی را از آزمون محلی و تأیید عملی روی دستگاه هدف جدا می‌کند. موفقیت CI به معنی اثبات ورود به حساب ChatGPT، دسترسی مهمان، یا پایداری شبکه و Chrome روی رایانهٔ مقصد نیست.

## انجام‌شده در کد

- [x] پایگاه SQLite مستقل، مهاجرت‌های شماره‌دار با checksum و تراکنش‌ها؛ دیتابیس یادگیری از دیتابیس اصلی برنامه جدا است.
- [x] ذخیرهٔ پایدار درخواست‌های صریح یادگیری با شناسهٔ درخواست و ترتیب FIFO.
- [x] maintenance دوره‌ای AI-learning علاوه بر startup، وظایف `learning.run_job` فاقد task متناظر را با reconciliation idempotent ترمیم می‌کند؛ خطای این مرحله جداگانه log می‌شود و maintenance factual/browser-learning ادامه می‌یابد. این repair دوره‌ای است و atomic outbox محسوب نمی‌شود؛ قرارداد در ADR-017 ثبت شده است.
- [x] بازیابی دستی اجرای ناتمام از صف سراسری استفاده می‌کند؛ در نبود اجرای ذخیره‌شده، مسیر ادامهٔ سرفصل‌های تأییدشده نیز سرفصل واجد شرایط را مستقیماً از SQLite پیدا می‌کند و به صفحه‌بندی ۱۰۰ دوره/۵۰ اجرا وابسته نیست. آزمون رگرسیون، دورهٔ دارای سرفصل ناتمام خارج از صفحه را پوشش می‌دهد.
- [x] بازیابی اجرای صف‌شده/ناتمام هنگام راه‌اندازی، مگر آنکه مکث سراسری فعال باشد؛ پس از پایان کار، worker درخواست ذخیره‌شدهٔ بعدی را بررسی می‌کند. مسیر دستی «ادامه/بازیابی» نیز اکنون قدیمی‌ترین اجرای قابل‌بازیابی را از صف پایدار سراسری انتخاب می‌کند و به محدودیت صفحه‌بندی ۱۰۰ دوره/۵۰ اجرا وابسته نیست؛ آزمون رگرسیون، اجرای خارج از صفحهٔ داشبورد را پوشش می‌دهد.
- [x] پاسخ سرفصل فقط وقتی موفق محسوب می‌شود که خط `AUDIT` صریحاً `COMPLETE` باشد، تعداد سرفصل‌های اعلام‌شده با متن قابل‌استخراج تطبیق کند و شماره‌گذاری از ۱ پیوسته باشد؛ پاسخ ناقص/بدون ممیزی همراه متن خام و سرفصل‌های قابل استخراج ذخیره می‌شود، اما اجرا در وضعیت نیازمند اقدام می‌ماند و تولید درس خودکار شروع نمی‌شود.
- [x] اگر بررسی معنایی عنوان‌های تکراری به‌دلیل در دسترس نبودن Ollama/مدل embedding شکست بخورد، پاسخ خام outline پیش از خروج از تراکنش ذخیره می‌شود؛ سرفصل جدیدی بدون بررسی تکرار درج نمی‌شود و اجرا برای بازیابی می‌ماند.
- [x] جلوگیری از عنوان تکراری برای دوره، سرفصل و درس هنگام ایجاد/ویرایش؛ outline جدید با عناوین موجود و عنوان‌های همان batch مقایسه می‌شود، حتی وقتی دوره هنوز سرفصلی ندارد. مقایسهٔ معنایی در دسته‌های حداکثر ۶۴تایی انجام می‌شود؛ اگر برای عنوان‌های مبهم سرویس embedding در دسترس نباشد، ثبت مورد بررسی‌نشده متوقف می‌شود. پاسخ تولیدشده در مسیر worker حفظ می‌شود.
- [x] فهرست سرفصل‌ها و درس‌ها در یک منوی جمع‌شونده قرار دارد؛ هر سرفصل نیز جداگانه باز/بسته می‌شود و فهرست درس‌ها و نسخه‌های محتوا در زیرمنوی همان کاتالوگ باز می‌شود.
- [x] خطاهای ورود ChatGPT، تأیید انسانی و محدودیت درخواست با کدهای مشخص ثبت می‌شوند؛ هیچ تلاش خودکاری برای دور زدن این محدودیت‌ها انجام نمی‌شود.
- [x] لاگ چرخشی تشخیصی بدون ثبت متن کامل prompt/پاسخ؛ رویدادها و نوع خطا برای عیب‌یابی ثبت می‌شوند.
- [x] ارزیابی آفلاین و تکرارپذیر پاسخ و بازیابی: پوشش مفهوم‌های مورد انتظار، ادعاهای ممنوع، وجود منبع مورد انتظار، precision/recall، شناسه‌های ممنوع و جلوگیری از نشت chunkهای غیرمجاز.
- [x] نرمال‌سازی فارسی/عربی برای ی/ي، ک/ك، اعراب و فاصله‌گذاری در ارزیابی.
- [x] تست‌های رگرسیون برای محتوای فارسی تکراری، منابع غیرقابل‌اعتماد، جلوگیری از انتشار بدون تأیید، و بازیابی دانش منتشرشده.
- [x] دروازهٔ شواهد درس در نسخهٔ `lesson-evidence-v4` فقط URLهای HTTPS بدون userinfo و با پورت استاندارد 443 (یا پورت پیش‌فرض) را می‌پذیرد؛ URL با userinfo خالی، پورت خالی یا پورت غیراستاندارد نه منبع قابل‌استناد محسوب می‌شود و نه در شمارش دامنهٔ اصلی وارد می‌شود. این کنترل شکل authority را اعتبارسنجی می‌کند و اثبات‌کنندهٔ صحت محتوای منبع نیست.
- [x] API بازخورد جست‌وجو: هر پاسخ جست‌وجو یک trace_id دارد؛ امتیاز مفید/غیرمفید با POST /api/ai-learning/feedback ذخیره و آمار تجمیعی از GET /api/ai-learning/feedback/summary دریافت می‌شود.
- [x] حریم خصوصی بازخورد: متن خام جست‌وجو در trace ذخیره نمی‌شود؛ فقط SHA-256، شناسه‌های chunk، امتیاز و توضیح اختیاری محدودشده ذخیره می‌شود. ثبت مجدد بازخورد برای همان trace رکورد تکراری ایجاد نمی‌کند.
- [x] انتشار همچنان صریح است: متن دریافت‌شده خودکار منتشر نمی‌شود؛ سرفصل باید تأیید، نسخه بازبینی و سپس منتشر شود.
- [x] بررسی وابستگی‌های کد قدیمی انجام شده است؛ افزونهٔ Chrome حذف نشده چون هنوز fallback مستند و تحت آزمون بسته‌بندی/مجوزهاست. موردی که بلااستفاده بودن آن اثبات نشده باشد، حذف نشده است.
- [x] مستندات راه‌اندازی، feature flagها، محدودیت‌های صف، بازیابی، بازبینی/انتشار و API بازخورد به‌روزرسانی شده‌اند.

- [x] کلید idempotency اجرای یادگیری با fingerprint پایدار از دوره، نوع اجرا، حالت انتخاب، شناسه‌های اولیهٔ سرفصل‌ها و سیاست retry ثبت می‌شود؛ استفادهٔ مجدد از همان کلید برای درخواست متفاوت رد می‌شود. مهاجرت شمارهٔ ۵ ستون nullable اضافه می‌کند تا رکوردهای قدیمی بدون بازنویسی داده حفظ شوند؛ برای رکوردهای قدیمی فقط فیلدهای قابل‌اثبات اعتبارسنجی می‌شوند. آزمون رگرسیون تعارض دوره، سرفصل و سیاست retry را پوشش می‌دهد.

- [x] هر سرفصل انتخاب‌شده پیش از شروع مرورگر، یک اجرای مستقل و پایدار در SQLite می‌گیرد؛ مسیر ادامهٔ دستی و بازیابی runهای قدیمی نیز سرفصل‌های باقی‌مانده را پیش از شروع worker در صف ثبت می‌کند. صف FIFO پس از پایان هر اجرا مورد بعدی را dispatch می‌کند؛ بنابراین قطع برنامه فهرست سرفصل‌ها را در حافظهٔ worker گم نمی‌کند. سرفصل مکث‌شده در صف باقی می‌ماند اما dispatcher و بازیابی آن را اجرا نمی‌کنند؛ با برداشتن مکث، صف دوباره فعال می‌شود. مکث اجرای فعال، آن را به‌صورت قابل‌بازیابی در صف نگه می‌دارد و لغو دائمی محسوب نمی‌شود؛ تکمیل هم‌زمان پاسخ نیز در تراکنش SQLite با وضعیت مکث هماهنگ می‌شود تا درس در زمان مکث ذخیره نشود. اجرای دارای صف پایدار در همان دوره گسترش داده نمی‌شود تا تولید تکراری یا خارج از انتخاب کاربر رخ ندهد. تست‌های رگرسیون restart، ادامهٔ legacy، مکث/ادامهٔ سرفصل و رقابت مکث/تکمیل این رفتارها را پوشش می‌دهند.

## محدودیت‌های فنی شناخته‌شده

- صف `app/ai_learning/` همچنان یک worker مرورگر درون‌پردازه‌ای دارد، اما مالکیت آن اکنون با lease پایدار SQLite بین فرایندها هماهنگ می‌شود: owner token مختص فرایند، fencing epoch افزایشی، انقضای ۹۰ ثانیه و heartbeat هر ۱۵ ثانیه. claim، dispatch، بازیابی startup، resume و نوشتن worker زیر این lease انجام می‌شوند؛ نوشتن مالک منقضی‌شده در همان تراکنش رد می‌شود. این طراحی فقط فرایندهایی را هماهنگ می‌کند که همان دیتابیس محلی و پروفایل Chrome را به اشتراک می‌گذارند؛ صف چندمیزبانه یا مناسب network filesystem نیست. ادامهٔ دقیق generation یا تب ChatGPT پس از قطع فرایند همچنان تضمین نمی‌شود.
- اگر برنامه پس از ارسال prompt و پیش از ذخیرهٔ پاسخ متوقف شود، پاسخ ChatGPT ممکن است دوباره درخواست شود. ادامهٔ دقیق همان generation از سمت ChatGPT قابل تضمین نیست.
- اگر ممیزی outline ناقص باشد، متن خام و سرفصل‌های قابل استخراج حفظ می‌شوند؛ برای تکمیل، اجرای دریافت سرفصل را دوباره آغاز کنید تا موارد قبلی deduplicate شوند. ادامهٔ خودکار همان پیام/نسل در رابط ChatGPT تضمین نشده است.
- اتوماسیون بر رابط بصری ChatGPT و DOM آن متکی است. تغییرات رابط، ورود، CAPTCHA/تأیید انسانی، محدودیت استفاده، یا قطع شبکه می‌تواند کار را به وضعیت نیازمند اقدام کاربر ببرد.
- ارزیابی فعلی، آزمون‌های قانون‌محور و قابل تکرار است؛ اثبات صحت واقعی ادعاها یا ارزیابی داور-مدل (LLM-as-judge) نیست.
- رابط جست‌وجوی دانش و جریان اصلی چت اکنون کنترل‌های مفید/غیرمفید دارند؛ بازخورد هر پاسخ چت به شناسهٔ پیام متصل و به‌صورت پایدار ذخیره می‌شود، اما فقط سیگنال سودمندی است و هیچ مسیر خودکاری برای ارتقای دانش یا وضعیت راستی‌آزمایی ندارد. حذف گفتگو نیز بازخورد وابسته به پیام را با cascade حذف می‌کند.
- بررسی خودکار URL، دسترسی‌پذیری و محدودیت‌های SSRF وجود دارد، اما پاسخ HTTP موفق به‌تنهایی ثابت نمی‌کند که منبع ادعا را پشتیبانی می‌کند؛ بررسی محتوایی منبع همچنان به بازبینی نیاز دارد.
- بررسی embedding معنایی به مدل محلی Ollama وابسته است. نبود مدل باید واضح گزارش شود؛ تست‌های CI برای سنجش‌های deterministic به مدل خارجی وابسته نیستند.

## گام‌های باقی‌مانده برای پذیرش

1. اجرای محلی/انسانی روی ماشین هدف: Chrome واقعی، حساب واردشده و حالت مهمان ChatGPT، مکث/ادامه، قطع شبکه، timeout و restart در میانهٔ capture.
2. ارزیابی انسانی کیفیت محتوای تولیدشده و کفایت منابع؛ benchmarkهای deterministic و smoke مرورگر جایگزین داوری انسانی یا آزمون زندهٔ ChatGPT نیستند.
3. هماهنگی مالکیت worker بین فرایندهای یک میزبان با lease/heartbeat و fencing در کد پیاده‌سازی و با آزمون رقابت فرایندی، انقضای lease، بازیابی و رد نوشتن مالک قدیمی پوشش داده شده است. پذیرش crash/soak روی میزبان هدف همچنان باز است؛ چندمیزبانه و network filesystem پشتیبانی نمی‌شوند.
- اجرای موفق main پس از تغییرات صف/ارزیابی: [tests](https://github.com/cognitive-kernel/Personal-AI-assistant/actions/runs/40343292998)، [browser E2E](https://github.com/cognitive-kernel/Personal-AI-assistant/actions/runs/40343292937)، [dependency audit](https://github.com/cognitive-kernel/Personal-AI-assistant/actions/runs/40343293027).
- آخرین CI مرتبط با قابلیت‌های AI-learning: PR #631 روی head دقیق `e280fb20458e09c8eb098d20734c57a8172842da` با 1740 passed و 5 skipped، Windows storage، Chromium dashboard smoke و dependency audit موفق شد؛ [tests #41170165292](https://github.com/cognitive-kernel/Personal-AI-assistant/actions/runs/41170165292)، [browser E2E #41170165467](https://github.com/cognitive-kernel/Personal-AI-assistant/actions/runs/41170165467)، [dependency audit #41170165290](https://github.com/cognitive-kernel/Personal-AI-assistant/actions/runs/41170165290). PR #642 نیز CI کامل روی head خود را با 1752 passed/5 skipped گذراند، اما تغییر آن test-only است. هیچ‌یک از این شواهد جایگزین ورود واقعی به ChatGPT، بررسی منابع زنده یا پذیرش میزبان هدف نیستند.
- PR #645 ادغام شد: خطای enqueue یک job دیگر jobهای بعدی را گرسنه نمی‌کند؛ خطای query اولیه در startup ثبت می‌شود و به maintenance دوره‌ای واگذار می‌شود. دو regression برای هر دو مسیر اضافه شدند و CI پس از ادغام موفق شد.
- تست ورود واقعی به ChatGPT، تست با حساب کاربر، قطع برق/شبکه روی دستگاه مقصد، و سنجش کارایی با مدل embedding نصب‌شده، عمداً خارج از CI خودکارند و هنوز باید عملی انجام شوند.

- `GET /favicon.ico` پاسخ `404` داد؛ این خطا در لاگ دیده شد اما صفحه و APIهای ذکرشده همچنان پاسخ موفق داشتند.
- در startup، بازیابی صف `idle` گزارش شد؛ این به معنی آزموده‌شدن بازیابی یک کار ناتمام نیست.

این نتایج فقط تست خودکار و smoke اولیهٔ سرور/رابط را تأیید می‌کنند. دریافت واقعی outline از ChatGPT، ذخیرهٔ پایدار درس، جلوگیری از تکرار از مسیر واقعی UI/worker، عملکرد منوی جمع‌شونده در مرورگر، تأیید سرفصل، و سناریوهای timeout/قطع شبکه/restart هنوز در شواهد این اجرا تأیید نشده‌اند. پذیرش end-to-end باز است.

## گام‌های باقی‌مانده

1. اجرای CI کامل برای همین تغییرات؛ رفع هر خطای قابل‌بازتولید و تکرار CI تا موفقیت.
2. آزمون browser E2E برای کنترل‌های مفید/غیرمفید پنل جست‌وجوی یادگیری اضافه شده است: محتوای محلیِ منتشرشده در دیتابیس موقت seed می‌شود، شناسهٔ trace هر درخواست با payload بازخورد تطبیق داده می‌شود و شمارنده‌های پایدار بررسی می‌شوند. پذیرش این مورد منوط به موفقیت CI روی SHA دقیق PR است؛ این آزمون جایگزین ارزیابی انسانی کیفیت مدل نیست.
3. lease/heartbeat مستقل برای صف `app/ai_learning/` پیاده‌سازی شده و آزمون‌های چندفرایندی، fencing، بازیابی lease منقضی‌شده و ایمنی reset در CI وجود دارند. این قابلیت فقط روی یک میزبان با دیتابیس SQLite و پروفایل Chrome مشترک معتبر است؛ crash/soak و بازیابی عملی روی میزبان هدف همچنان نیازمند پذیرش محلی است.
4. اجرای تست عملی محلی/دستگاهی برای Chrome، ورود/مهمان، مکث/ادامه، قطع اتصال و بازیابی؛ این بخش نیازمند مرورگر و دسترسی واقعی به ماشین هدف است و از طریق بررسی مخزن یا تست CI قابل اثبات نیست.

## Worker startup failure recovery

All learning entry points use one worker-start boundary. If `thread.start()` raises, the in-memory active markers and cancellation event are cleared, and the durable run is returned to the queued state for a later dispatch. The failure is logged with its exception type and bounded message; the caller receives a typed `worker_thread_start_failed` error. This avoids leaving a phantom `running` record with no worker. Regression coverage verifies the queue can dispatch the same run after a subsequent successful start. This repository test does not replace target-host Chrome/process-restart acceptance.


## اثبات بازیابی پس از process restart

`tests/test_ai_learning_retrieval_boundary.py::test_published_knowledge_is_retrievable_after_a_new_process` یک فرایند Python تازه را با همان `AI_LEARNING_DB_PATH` اجرا می‌کند. فرایند تازه فقط نسخهٔ منتشرشده را از مسیر `integration.retrieve_context` دریافت می‌کند، نسخهٔ draft را نمی‌بیند و query trace را در همان SQLite ثبت می‌کند. این آزمون ماندگاری و قرارداد retrieval را می‌سنجد؛ کیفیت زندهٔ مدل یا صحت factual پاسخ را نمی‌سنجد.
