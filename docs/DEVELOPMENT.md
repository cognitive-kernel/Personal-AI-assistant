# راه‌اندازی محیط توسعه

نیازمندی اولیه سیستم: Python 3.11 یا جدیدتر. لانچر، Ollama و مدل انتخاب‌شده را هم بررسی می‌کند.

## اجرای خودکار

از ریشه مخزن اجرا کنید:

```bash
python run.py
```

لانچر پیش از اجرای برنامه:
1. محیط مجازی `.venv` را می‌سازد یا از محیط موجود استفاده می‌کند.
2. وابستگی‌های تعریف‌شده در `pyproject.toml` را بررسی می‌کند.
3. **حتی اگر بسته‌ای از قبل نصب باشد، نسخه سازگار آن و وابستگی‌های لازم را در `prerequisites/wheels` نگه می‌دارد.** اگر مخزن محلی کامل و سالم باشد، دانلود را تکرار نمی‌کند؛ در غیر این صورت ابتدا بسته‌های موجود را استفاده می‌کند و فقط موارد لازم را دریافت می‌کند.
4. بسته‌های موردنیاز را در صورت نیاز از مخزن محلی نصب می‌کند.
5. نصب‌کننده رسمی Ollama را در `prerequisites/installers` cache می‌کند. اگر Ollama نصب نباشد، لانچر در Windows نصب‌کننده را اجرا می‌کند و در Linux اسکریپت رسمی را اجرا می‌کند. در macOS آرشیو رسمی را ذخیره و باز می‌کند تا نصب تعاملی تکمیل شود.
6. دسترسی به سرویس Ollama و وجود مدل را بررسی می‌کند؛ مدل پیش‌فرض `qwen2.5:7b` است و در صورت نبودن با Ollama دریافت می‌شود.
7. سرور فقط پس از آماده‌شدن پیش‌نیازها اجرا می‌شود.

فهرست بسته‌ها و اثرانگشت مخزن در `prerequisites/manifest.json` نگهداری می‌شود. تغییر وابستگی‌ها، محیط پایتون یا پلتفرم باعث بازبینی cache خواهد شد. این پوشه محلی است و در Git ثبت نمی‌شود.

گزینه‌ها:
- `python run.py --check-only`: آماده‌سازی پیش‌نیازها بدون اجرای سرور.
- `python run.py --dev --check-only`: آماده‌سازی وابستگی‌های توسعه و آزمون بدون اجرای سرور.
- متغیر `OLLAMA_MODEL`: تغییر مدل موردنیاز.

## اجرای آزمون‌ها

```bash
python run.py --dev --check-only
.venv/bin/python -m pytest
```

در Windows از `.venv\\Scripts\\python.exe -m pytest` استفاده کنید.

اگر نصب‌کننده سیستم‌عامل به مجوز مدیریتی یا تأیید تعاملی نیاز داشته باشد، باید آن مرحله را کامل کنید. اگر دانلود ناموفق باشد، برنامه متوقف می‌شود تا محیط ناقص اجرا نشود.

پایگاه داده‌ها در اولین راه‌اندازی ساخته می‌شوند. مسیرهای پیش‌فرض `data/settings.db` و `data/learning.db` هستند.


برای فرایند کنترل‌شدهٔ به‌روزرسانی، پشتیبان، بازیابی staging و rollback به [runbook عملیات محلی](operations/INSTALL_UPDATE_ROLLBACK.md) مراجعه کنید.


## ممیزی چرخه‌های وابستگی ماژول‌ها

برای گزارش چرخه‌های import در بستهٔ برنامه، بدون اجرای یا import کردن کد برنامه:

```bash
python scripts/check_import_cycles.py
```

این ابزار با AST گراف وابستگی ماژول‌های Python را می‌سازد و مؤلفه‌های قویاً همبند را گزارش می‌کند. در حالت پیش‌فرض فقط گزارش می‌دهد تا چرخه‌های فعلی پیش از تبدیل‌شدن به مانع CI بررسی شوند. پس از بررسی و تعیین تکلیف چرخه‌های موجود، می‌توان آن را با `--fail-on-cycle` به دروازهٔ CI تبدیل کرد. این تحلیل ایستا همهٔ importهای پویا، aliasهای زمان اجرا یا وابستگی‌های غیرمستقیم خارج از بسته را کشف نمی‌کند؛ نتیجهٔ بدون چرخه به‌تنهایی اثبات کامل جداسازی معماری نیست.

### نتیجهٔ نخستین اجرای CI — 2026-10-17

اجرای workflow آزمون روی commit `2e9cb66a1f63bdddd36389424782d8085d6a84fb`، ۵۵ ماژول Python را بررسی کرد و دو مؤلفهٔ چرخه‌ای گزارش داد:

- `app.experience -> app.experience_feedback -> app.experience_retrieval`
- `app.learning -> app.learning_tasks`

این نتیجه در گزارش job شمارهٔ `117315635809` ثبت شده است. بررسی اولیهٔ کد نشان می‌دهد مسیر تجربه شامل facade بازیابی تنبل در `experience.py` و وابستگی‌های feedback/retrieval است؛ این گزارش به‌تنهایی ثابت نمی‌کند که در زمان اجرا خطای import رخ می‌دهد. مؤلفهٔ learning/learning_tasks نیز نیازمند بررسی وابستگی‌ها و مالکیت مسئولیت‌هاست. فعلاً این موارد یافته‌های باز معماری هستند: در این PR رفتار runtime تغییر نمی‌کند و gate سخت‌گیرانه فعال نمی‌شود. برای رفع چرخه‌ها باید refactor جداگانه با آزمون‌های رگرسیون و CI انجام شود.
