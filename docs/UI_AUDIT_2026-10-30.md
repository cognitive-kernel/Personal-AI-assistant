# Day 1 UI audit — 2026-10-30

**Baseline:** `main` at `f403ae13a03a9ac5e526879d40380221c879cff8` (after PR #571).
**Scope:** static dashboard structure, navigation implementation, UI acceptance criteria, semantic/contrast tests, and browser E2E test inventory. This is a repository-level audit; it does not claim manual screen-reader or target-host acceptance.

## Verified baseline

- `app/static/index.html` contains 17 section elements in total: 15 top-level sections and 2 nested sections. Excluding the storage-degraded banner, 16 sections represent workflow/content areas.
- The persistent navigation exposes 14 primary destinations. `test_dashboard_navigation_and_layout_are_accessible_and_responsive` checks each destination's navigation link and section, verifies its route returns HTTP 200, and confirms the chat home hides non-chat sections.
- The browser suite contains 27 independent `test_*` functions.
- The static dashboard contains 56 buttons. `test_static_dashboard_buttons_declare_explicit_valid_types` checks every static button for an explicit valid `type`.
- `test_core_theme_tokens_meet_wcag_text_contrast` checks core light/dark design tokens; it is not a rendered-state contrast audit.
- `page-navigation.js` sets the active route's navigation link to `aria-current="page"`. This is page navigation, not scroll-position/current-location navigation.

## Gaps and limits retained as open

1. The acceptance ledger's navigation description was stale: it said `aria-current=location` and scroll/resize/hash updates. The current implementation and browser assertion use `aria-current=page`; this audit corrects the documentation rather than changing working page-navigation behavior.
2. Navigation presence and HTTP 200 checks do not prove complete interaction parity for every destination. The browser suite does not yet provide an end-to-end interaction/error-state matrix for every primary workflow, particularly the distinct cloud planning/quota and OCI flows, sandbox execution, programming assistance, knowledge browsing, and settings beyond theme persistence. These are candidates for focused follow-up after inspecting their API contracts and existing backend tests; absence of a browser test alone is not proof of a broken feature.
3. Automated Chromium checks do not satisfy manual keyboard-only and screen-reader review.
4. Token-level contrast checks do not satisfy rendered component/state contrast review.
5. CI browser coverage is not target-host usability or operational acceptance.

## Day 2 entry criteria

For each candidate workflow above, map the UI action to its API endpoint, existing backend tests, success/loading/empty/error states, consent or confirmation boundary, and data-persistence behavior. Add only the missing browser assertions. Fix only a reproduced defect with a regression test. Do not broaden scope by adding duplicate navigation tests.

| Knowledge base | `test_knowledge_base_routes.py`, `test_knowledge_base.py` | Verify source add/list/search interactions and visible validation/error states in Chromium |

The browser CI workflow starts an isolated local application with disposable databases, enables the AI-learning module, installs Chromium, and runs `pytest -q tests/test_browser_e2e.py`. Thus the 27 browser test functions are actively exercised in the dedicated CI workflow rather than merely collected.

This mapping narrows the gap: most candidate areas have backend/API and/or static UI-contract tests. The remaining UI acceptance risk is chiefly realistic browser interaction and state feedback, not an absence of all automated tests. The next audit step should select a small number of highest-value browser flows and inspect their actual event handlers before adding coverage.
