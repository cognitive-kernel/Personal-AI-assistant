# بهینه‌سازی سرعت، دقت و کیفیت یادگیری

- وضعیت: مشخصات اجرایی و دفتر وضعیت پیاده‌سازی
- دامنه: هر چهار مسیر یادگیری، پژوهش موضوعی، ارزیابی کد، بازیابی دانش و سیستم تجربه
- اصل: افزایش سرعت نباید باعث حذف منبع، کوتاه‌کردن پوشش موضوع، پذیرش دانش تأییدنشده یا ضعیف‌کردن آزمون شود.

این سند مرجع تصمیم‌ها، تغییرات انجام‌شده، کارهای در حال انجام و شکاف‌های باقی‌مانده است. وضعیت «موجود» فقط به معنی وجود کد/آزمون در مخزن است؛ اثربخشی عملیاتی باید با CI و سپس آزمون محیط هدف جداگانه اثبات شود.

## 3. بهینه‌سازی‌های سرعت

### 3.1 اولویت بالا — اندازه‌گیری قبل از تغییر
برای هر task باید زمان صف، زمان جست‌وجو، دریافت صفحه، استخراج، هر فراخوانی مدل، repair، ارزیابی، ذخیره‌سازی و زمان کل ثبت شود. آمار باید شامل p50/p95، تعداد retry، timeout، token ورودی/خروجی، حافظه، مدل/provider و تعداد منابع باشد. بدون خط مبنا، ادعای «سریع‌تر» پذیرفته نیست.

### 3.2 بازیابی منابع
- جست‌وجوهای مستقل را فقط با concurrency محدود، timeout و rate-limit اجرا کن؛ ترتیب ادغام نتایج باید deterministic باشد.
- cache منبع بر اساس URL canonical و content hash بساز؛ داده قدیمی را به‌جای حذف، نسخه‌بندی کن.
- TTL را بر اساس نوع منبع تعیین کن: release/security/advisory کوتاه‌تر از مفاهیم evergreen.
- قبل از استفاده مجدد، freshness را بررسی کن؛ برای release watch، cache هرگز جای بررسی تغییرات جدید را نگیرد.
- fetch تکراری یک URL در یک task را حذف کن و خطاهای fetch را با نوع خطا ثبت کن.
- منابع را بر اساس query، موضوع، نسخه و claim دسته‌بندی کن؛ همه منابع جمع‌آوری‌شده باید در synthesis مصرف یا با دلیل صریح کنار گذاشته شوند.

### 3.3 تولید و ارزیابی مدل
- promptهای تکراری را نسخه‌دار و قابل cache کن؛ فقط ورودی‌های کاملاً همسان و مدل/نسخه همسان قابل استفاده مجددند.
- محتوای منبع را به بخش‌های مرتبط با موضوع/claim تقسیم کن؛ خلاصه‌سازی نباید مرجع اصلی یا hash متن کامل را جایگزین کند.
- از batchهای تطبیقی بر اساس اندازه واقعی متن و ظرفیت context استفاده کن؛ در صورت نزدیک‌شدن به محدودیت، checkpoint و ادامه بده، نه truncate.
- repair فقط برای خطای ساختاری/قراردادی و با تعداد تلاش محدود اجرا شود؛ شکست باید قابل مشاهده بماند.
- فراخوانی ارزیاب مستقل را فقط برای ادعاهای نیازمند ارزیابی انجام بده؛ نتیجه هرگز توسط همان مدل تولیدکننده تأیید نشود.
- وظایف مستقل را می‌توان موازی کرد؛ درس‌های دارای پیش‌نیاز و مراحل وابسته باید ترتیبی بمانند.

### 3.4 صف و ذخیره‌سازی
- idempotency، deduplication و unique constraints باید از اجرای دوباره کار جلوگیری کنند.
- کارها باید lease، heartbeat، retry با backoff و checkpoint داشته باشند.
- نوشتن‌های پرتکرار را batch کن، اما مرز transaction و بازیابی را حفظ کن.
- queryهای پرتکرار را با EXPLAIN و benchmark بررسی کن؛ index فقط بر اساس الگوی واقعی query اضافه شود.
- taskهای مستقل را با سقف هم‌زمانی و سهمیه منابع اجرا کن تا مدل محلی و RAM اشباع نشوند.

## 4. بهینه‌سازی‌های دقت

1. **Claim-level grounding:** درس به ادعاهای اتمی تقسیم شود؛ هر ادعا منبع، نسخه، تاریخ و وضعیت پشتیبانی مستقل داشته باشد.
2. **Source diversity:** دامنه‌های مستقل، اسناد رسمی، release notes، استانداردها، کتاب‌ها و منابع عملیاتی بر اساس نوع ادعا ترکیب شوند؛ تعداد URL به‌تنهایی معیار استقلال نیست.
3. **Conflict detection:** ادعاهای متعارض با منبع و نسخه‌شان نگهداری شوند؛ تا حل تعارض، خروجی unverified/inconclusive باشد.
4. **Version scoping:** هر مثال و دستور باید نسخه، سیستم‌عامل، معماری، edition و پیش‌نیازهای مرتبط را مشخص کند.
5. **Temporal validity:** تاریخ انتشار محصول از تاریخ اصلاح مستندات و تاریخ دریافت جدا باشد؛ تغییر release یا EOL، ادعاهای وابسته را stale کند.
6. **Independent evaluation:** تولیدکننده داور خودش نیست؛ verifier باید هویت، نسخه، روش و evidence ref داشته باشد.
7. **Adversarial tests:** ورودی مرزی، مثال نقض، نسخه قدیمی، API منسوخ، خطای محیط، prompt injection و منابع متناقض پوشش داده شوند.
8. **Semantic grading:** پارافریز معتبر پذیرفته شود؛ خطای مفهومی از تفاوت لفظی، ابهام سؤال یا نبود runtime تفکیک شود.
9. **Calibration:** confidence با نرخ خطای واقعی در benchmark نسخه‌دار سنجیده شود؛ confidence مدل به‌تنهایی شاهد نیست.
10. **Regression:** هر شکست قابل‌بازتولید به آزمون رگرسیون و اصلاح نسخه‌ای درس/دانش تبدیل شود.

## 5. ارزیاب عمومی کد

ارزیاب کد باید یک قابلیت مشترک باشد که هر چهار مسیر یادگیری بتوانند از آن استفاده کنند؛ نه مسیر یادگیری پنجم.

چرخه الزامی:
1. ثبت زبان، نسخه runtime، وابستگی‌ها، سیستم‌عامل، معماری، hash و revision کد.
2. تولید/دریافت تست‌های عادی، مرزی، منفی، property-based و امنیتی متناسب با ریسک.
3. تعریف oracle مستقل از کد و مدل تولیدکننده؛ expected output نباید از اجرای همان کد استخراج شود.
4. اجرا در Sandbox ایزوله، بدون شبکه و با محدودیت CPU/RAM/زمان/فایل‌سیستم.
5. ثبت stdout/stderr/exit code، ورودی، خروجی مورد انتظار، نتیجه، زمان و محدودیت محیط.
6. تفکیک failed از not_run و environment_unavailable.
7. محاسبه امتیاز از تست‌های معتبر اجراشده؛ تست اجرا‌نشده موفق نیست.
8. نگهداری همه تلاش‌ها و نسخه‌ها؛ اصلاح کد، آزمون مجدد را با revision جدید ایجاد می‌کند.

زبان‌های runtime موجود در زیرساخت باید جدا از پوشش واقعی تمرین‌ها گزارش شوند. در snapshot فعلی، زیرساخت Python/JavaScript/Rust موجود است، اما مجموعه تمرین عملی محدود است. گسترش به SQL و زبان‌های دیگر باید با sandbox و oracle مخصوص هر زبان انجام شود؛ پشتیبانی اسمی بدون آزمون واقعی پذیرفته نیست.

## 6. معیار دقت ۹۵٪ و خودمختاری

- معیار فعلی سیاست: accuracy تجمیعی **بیشتر از ۹۵٪**، نه مساوی آن، در شواهد مستقل هر چهار مسیر.
- هر رکورد باید sample ID یکتا، مسیر یادگیری، نتیجه، روش verifier، شناسه verifier، زمان timezone-aware و evidence ref داشته باشد.
- مدل مولد حق تأیید خروجی خودش را ندارد.
- آزمون اجرا‌نشده، evidence مفقود، نتیجه مبهم یا محیط unavailable موفق شمرده نمی‌شود.
- شکست‌ها از مخرج محاسبه حذف نمی‌شوند مگر اینکه طبق سیاست benchmark از ابتدا invalid شناخته شوند و علت آن append-only ثبت شود.
- gate باید با هر نتیجه جدید و regression دوباره محاسبه شود و در صورت افت به ۹۵٪ یا کمتر بسته بماند.
- پیش از فعال‌سازی عملیاتی، حداقل حجم نمونه، بازه اطمینان، تفکیک دامنه/زبان/نسخه و مقاومت در برابر data leakage باید تعریف و آزموده شود.
- این gate فقط برای پذیرش عادی محتوای کم‌خطر است؛ مجوز عملیات امنیتی، حریم خصوصی، حقوقی، مخرب یا production نیست.

## 7. داده‌های خام، تجربه و یادگیری از شکست

- هیچ مشاهده، پاسخ، منبع، تلاش، تجربه ناموفق یا نتیجه متناقض صرفاً به دلیل امتیاز پایین حذف نمی‌شود.
- داده خام immutable و دارای provenance می‌ماند؛ دانش تأییدشده نسخه‌دار و قابل rollback است.
- سیستم تجربه نتیجه هر چهار مسیر را دریافت می‌کند: موفق، ناموفق، inconclusive، اصلاح‌شده و آزمون‌نشده.
- retrieval باید دانش معتبر را از مشاهدات unverified و تجربه شکست‌خورده جدا کند؛ تجربه شکست فقط هشدار/سرنخ است، نه دستور معتبر.
- هر اصلاح به revision قبلی، دلیل، منابع جدید و آزمون رگرسیون پیوند می‌خورد.

## 8. Benchmark و داشبورد سنجش

حداقل شاخص‌ها:
- زمان کل و p50/p95 هر فاز؛ throughput منابع و درس‌ها؛ retry و نرخ شکست provider.
- دقت claim، پوشش citation، نرخ ادعای بی‌پشتوانه، نرخ تناقض و freshness.
- امتیاز آزمون عملی کد به تفکیک زبان/runtime/version و نوع تست.
- calibration خطای confidence، درصد پاسخ درست به موارد unanswerable و نرخ خطای زبان/نسخه.
- نرخ تکرار محتوای درس، موفقیت مرور، ماندگاری یادگیری و زمان رسیدن به mastery.
- هزینه token/زمان/منابع به ازای هر درس معتبر و هر مهارت تأییدشده.

Benchmark باید نسخه‌دار و جدا از داده تولید/آموزش باشد. هر بهینه‌سازی فقط وقتی پذیرفته است که latency یا هزینه را بهتر کند و معیارهای دقت/پوشش/امنیت را کاهش ندهد.

## 10. وضعیت تست و انتشار

- CI فقط برای SHA دقیق خودش معتبر است.
- موفقیت تست‌های UI یا security به معنی موفقیت کل suite نیست.
- تست محلی/انسانی محیط هدف در مرحله جداگانه انجام می‌شود؛ تا تکمیل و تأیید CI و کارهای GitHub، شروع آن اعلام نمی‌شود.
- هر قابلیت اجرا نشده باید NOT RUN بماند؛ هیچ ادعای سرعت، دقت یا خودمختاری بدون benchmark واقعی مجاز نیست.
